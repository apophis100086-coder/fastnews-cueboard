## 验收顺序

1. 固定相同材料与配置，记录两个客户端实际使用的提交号和运行目录。
2. 对照晨报、产品检索、人工勾选、初稿、修改保存、来源查看、复制和 Word 下载。
3. 检查刷新、停止、失败重试与切换入口后，原选择和旧稿是否完整。
4. 在隔离数据库中恢复旧资料并逐项核对，不操作正式库。
5. 分别记录程序通过、客户端响应、原文取得、稿件质量和人工采用；未验证项保持待验收。
6. 用户确认所需功能一致后，再合并主线并创建固定版本发行包。

## 长期维护方式

一个仓库、一套核心程序。每次修改建短期功能分支，完成检查后发起合并请求；正式版由已验收提交统一生成。两个客户端按相同提交工作，不各自重建一套看板。恢复旧代码使用有记录的回退；恢复业务数据使用对应的一致性备份。

GitHub 只放源码、测试、公开配置、说明和不含凭据的构建工具。数据库、上传资料、公司模板、样稿、运行环境、日志和任何账户配置仍按原规则留在本地。共享 API 包只能按原授权私下交付，不能作为普通仓库附件上传。

### 推送检查的隔离修复

首次在 Git worktree 中实际推送时，729 项测试中 5 项临时仓库测试失败，推送被阻止。原因是 hook 导出的 Git 仓库环境变量进入测试子进程，使临时 `git init/config` 误指向真实仓库。本地仓库的 bare、作者和 hook 配置已恢复，原版与整合版的提交和工作区均完整，业务库未涉及。修复为仅在独立测试进程中清除 Git 列出的仓库环境变量；新增回归检查在临时仓库中初始化和修改配置后，原测试仓库配置字节保持一致。完整历史扫描与全套测试仍保留，未绕过推送检查。

Windows 启动配置脚本还修复了重复编码标记导致参数解析失败的问题；新增只解析、不执行脚本的参数回归检查。测试产生的本整合目录快捷方式已按所有权核对后清除，未保留新增开机启动。

依据：[Git 官方 hook 文档](https://git-scm.com/docs/githooks#_description) 要求进入其他仓库时清除本仓库环境变量。后续完整结果记录在整合 PR 中。
