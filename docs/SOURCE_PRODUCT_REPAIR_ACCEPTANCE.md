## 原因与实际改动

| 原问题 | 实际修复 | 主要文件 |
|---|---|---|
| 原登记的晨报未实现列表采集，官方来源占满页面 | 读取财联社两个公开栏目内的结构化列表元数据；首页单列六类晨报与缺口 | `fastnews/live_sources.py`、`config/live_sources.yaml`、`fastnews/static/` |
| 二轮只整理旧事件池，没有补取专项固定源 | 先获取原 preferred_sources 及两类补充晨报，入库后重新路由；每源失败独立 | `fastnews/product_discovery.py`、`fastnews/research.py` |
| 下拉框换产品后，研究仍使用旧 Edition | 点击检索时按当前产品、日期、新闻与行情截点建立或复用期次；服务端拒绝产品不一致请求 | `fastnews/server.py`、`fastnews/static/app.js` |
| 首发时间未知导致排序失效；所有产品展示同一个池 | 不虚构首发与分数，另用观察变量和报道窗口分组；先呈现匹配摘要，保留原晨报链接 | `config/research_discovery.yaml`、`fastnews/routing.py` |
| 无关信息填满12个候选 | 专项、背景、人工探索分别处理，未命中项留在“全部事件池”；不凑候选数 | `fastnews/research.py` |
| FDA日期均被当作未知，可能把旧条目混入近期 | 保存来源显式带时区的CMS报道时间；旧记录保留的CMS时间仅作检索年龄依据；首次公开仍为null | `fastnews/live_sources.py`、`fastnews/product_discovery.py` |
| 看到FDA就当作创新药相关 | 药物/临床等词语需实际命中；兽药、猫狗用药等不列入创新药专项；FDA缩写本身不足 | `config/research_discovery.yaml` |
| 后于截点的报道仍被当作时间未知 | 首发未知且报道明确晚于截点时，归入截点外；早期事实不根据后来报道推造 | `fastnews/metadata.py` |

原26来源、21晨检标记、9主题、4产品配置不变。新展示词表是有版本的覆盖层，不是持仓清单或语义判断。没有改原40份交接文件，没有数据库破坏性迁移。

## 使用方法

先选“新闻日期”并获取当天信息，看上方“各类晨报”。需要产品检索时展开下方区域：选产品 → 选择截点按钮 → 点击“检索该产品线索”。无需先手动点“建立本期”。换产品后直接再检索。

首次公开时间缺失的材料会显示“时间待核实”。点击原始页面核对，或导入授权材料建立事实；最后选哪条、如何组织，仍由用户决定。
